## Ближайшее (когда треков станет заметно больше)

### 1. Ленивая загрузка каталога
**Проблема.** `src/data/index.js` собирает ВСЕ профили треков через
`import.meta.glob` с `eager: true` — они попадают в основной бандл. Сейчас это
28 профилей с массивами по 160 чисел каждый, то есть десятки килобайт, которые
грузятся до первого кадра.

**Решение.** Разделить: лёгкий индекс (id, название, артист, настроение) грузится
сразу, тяжёлый профиль (`waveform_peaks`, лирика) — по требованию через
динамический `import()`.

**Порог:** при ~100 треках. Сейчас преждевременно.

### 2. Разбиение бандла
**Проблема.** Один чанк 1.2 МБ (339 КБ gzip), Vite про это предупреждает при
каждой сборке. Основная масса — three.js и постпроцессинг.

**Решение.** `build.rollupOptions.output.manualChunks`: вынести three/R3F в
отдельный вендорный чанк — он меняется редко и будет кешироваться между
деплоями.

**Порог:** можно делать хоть сейчас, эффект — скорость повторных заходов.

### 3. HLS-нарезка вместо цельных файлов
**Проблема.** Сейчас перемотка на 2:30 требует докачки файла до этой точки,
а старт воспроизведения ждёт заметный кусок.

**Решение.** `ffmpeg -f hls -hls_time 6` даёт сегменты и манифест `.m3u8`.
Плюсы: мгновенный старт, перемотка качает только нужные сегменты, CDN кеширует
сегменты по отдельности. Минус: нужен `hls.js` (нативно HLS понимает только
Safari) плюс усложняется пайплайн.

**Порог:** когда появятся треки длиннее ~5 минут или счёт пойдёт на сотни.

### 4. Лесенка кодировок
**Решение.** Хранить мастер отдельно, раздавать 96/128/256 kbps и выбирать по
`navigator.connection.effectiveType` либо по подписке.

**Порог:** только вместе с бэкендом и реальной аудиторией на мобильных сетях.

## Требует бэкенда

### 5. Объектное хранилище вместо git
**Проблема.** 70 МБ mp3 лежат в репозитории. Для кураторского показа нормально,
для загрузок пользователей непригодно: каждая загрузка = коммит, размер растёт
неограниченно, у GitHub Pages мягкие лимиты 1 ГБ на сайт и 100 ГБ/мес трафика.

**Решение.** Кандидат №1 — **Cloudflare R2**: нулевая плата за исходящий трафик,
что для музыки решает (один трек 2.7 МБ × 1000 прослушиваний = 2.7 ГБ egress).
Метаданные — в D1/Postgres, байты — в R2, никогда наоборот.

**Порог:** первая же пользовательская загрузка.

### 6. Асинхронный пайплайн обработки
Загрузка → очередь → воркер (перекодирование в лесенку + анализ + нормализация
громкости) → пометка «готов». Скрипт импорта уже написан как прообраз такого
воркера: у него ровно те же шаги.

### 7. Нормализация громкости (EBU R128)
Хранить коэффициент усиления на трек, чтобы песни не скакали по уровню при
переключении. Считается тем же ffmpeg (`loudnorm`), кладётся в `audio_analysis`.

**Порог:** как только треки будут от разных исполнителей и из разных источников.

## Известные приближения (не баги, но стоит знать)

- **Темп определяется приблизительно.** Гребенчатый фильтр в
  `src/lib/audio/tempoEstimate.js` на нескольких треках промахивается на октаву
  (даёт удвоенный или вдвое заниженный темп). Свёртка к перцептивному центру
  ~120 BPM часть случаев чинит, но не все. Влияет только на частоту пульсации
  аватара. Правильное решение — библиотека уровня `aubio`/`essentia` в
  серверном пайплайне.
- **Кроссфейд между треками не работает.** Формула equal-power верна и покрыта
  тестами, но `AudioCrossfader` нигде не инстанцируется и вырезается
  тришейкингом: при одном `<audio>`-элементе сводить нечего. Нужен второй
  элемент и переключение источников.
- **GodRays пересоздаёт эффект и теряет render targets** при каждом ре-рендере
  (особенность `@react-three/postprocessing`). Смягчено через `memo`, но не
  устранено.

## 1. Что это за проект

MATplayer — генеративная 3D-платформа-плеер для «живого» знакомства слушателя с
исполнителями: не список треков, а интерактивный аудиореактивный опыт. Каждый
артист — «остров» в едином 3D-атласе, между островами камера летает по кривым
Безье. У каждого артиста — toon-shaded стилизованный не-человеческий
аватар-прокси (дышит/моргает процедурно, без риггинга и морф-таргетов), вокруг —
аудиореактивное облако частиц на curl-noise шейдере, пост-процессинг (bloom,
контуры, для меланхоличных треков — god rays/туман). Лирика синхронизируется
построчно и рендерится как оверлей.

Стек: React + React Three Fiber + Drei + Zustand + Web Audio API (AnalyserNode
для FFT) + кастомные GLSL-шейдеры + @react-three/postprocessing. Сборка — Vite,
деплой — GitHub Pages, статический сайт без бэкенда. Живая версия:
https://zazser82-methedron.github.io/MATplayer/

## 2. Что планировалось изначально (дизайн-спек, одобренный до реализации)

- Референсы исследования: кейсы Active Theory, Album Atlas, ARKx (Coala Music),
  PantoMatrix/JoyVASA.
- Объём v1: полная платформа на N артистов сразу (не один артист поэтапно) —
  рендеринг, аудио-движок, синхронизация лирики, генеративная тема по треку,
  навигация между артистами, UX-режимы (Focus/Ambient/Utility), мобильная
  адаптация, производительность, доступность.
- Явно вне объёма v1: аккаунты пользователей, загрузка треков конечными
  пользователями, бэкенд/хранилище/стриминг-инфраструктура, авто-анализ
  произвольного загруженного аудио, ИИ-генерация лицевой анимации/жестов.
- **Долгосрочный ориентир владельца проекта (важно для приоритизации
  рекомендаций):** в будущем — реальный музыкальный сервис с загрузкой треков
  пользователями, конкурирующий с SoundCloud/ВК Музыкой, плюс «нейроадаптация»
  через локальные/облачные нейросети. Модель данных трека/артиста спроектирована
  декларативно и без завязки на способ производства профиля именно для того,
  чтобы это будущее расширение не потребовало переделки движка рендеринга.
- Модель данных трека по спеку: `track_id`, `tempo_bpm`, `energy` (0–1), `mood`
  (строка-тег), `color_palette` (background/primary/secondary), `shader_presets`
  (`noise_type`: simplex_curly/laminar/turbulent_glitch, `outline_thickness`,
  `bloom_intensity`), `lyrics_ref`.
- Ожидалось: смысловые триггеры текста (ключевые слова лирики временно меняют
  форму частиц/шейдер), полноценный визуальный кроссфейд между островами
  (старая сцена растворяется в текстуру, пока камера уже летит к новой) с
  параллельным аудио-кроссфейдом 1.5–2 сек, BPM-синхронные пульсации через
  `web-audio-beat-detector`, лесенка деградации производительности
  (100k → 15k частиц → отключение bloom/AA → 2D-фолбэк), свайп вверх на
  мобильном → дискография/био артиста.

## 3. Что реально построено и работает сейчас

- Единый 3D-атлас с перелётом камеры (Bezier easing), toon-shaded аватар с
  процедурным дыханием/морганием, частицы на curl-noise (FFT bass/mid/treble
  реально управляют амплитудой), bloom пост-процессинг, построчная лирика с
  оверлеем и скринридер-дублем.
- Три UX-режима (Focus/Ambient/Utility) на основе idle-таймера, мобильная
  портретная адаптация камеры, свайп влево/вправо (треки/артисты), двойной тап
  (пауза), `prefers-reduced-motion` реально гасит камерные перелёты и
  аудиореактивные деформации.
- Контент: ЗМП/Cupsize — 3 трека с полными профилями (tempo/energy/mood/палитра)
  + все 26 текстов с таймингом уже перенесены; 2 контрастных по настроению
  placeholder-артиста без реального аудио.
- Только что добавлено: полноценная библиотека треков (модалка, поиск по
  названию/артисту/настроению), реальное переключение конкретного трека (не
  только артиста), prev/next-track с авто-переходом по окончании, во всех
  случаях аудио реально перезагружается и играет выбранный трек.
- 133 юнит/интеграционных теста, e2e smoke-тест на Playwright в CI.

## 4. Что написано в коде, но не подключено к реальному опыту («мёртвый код»)

Это важно учитывать в рекомендациях — часть работы уже сделана, её нужно не
изобретать заново, а **включить**:

- Класс аудио-кроссфейдера с формулой плавного перехода громкости (equal-power
  crossfade) существует и покрыт тестами, но нигде не создаётся во время
  выполнения — при смене артиста/трека звук сейчас режется резко (hard cut),
  никакого 1.5–2 сек кроссфейда нет, хотя весь расчёт для него уже написан.
- Детектор BPM (`web-audio-beat-detector`) подключён как зависимость и обёрнут
  тестируемой функцией, но никогда не вызывается во время воспроизведения — нет
  ни одной BPM-синхронной пульсации в визуале.
- Поле `shader_presets.noise_type` (simplex_curly/laminar/turbulent_glitch)
  задаётся в данных каждого трека и проходит валидацию схемой, но частицы всегда
  используют один и тот же фиксированный curl-noise алгоритм независимо от
  значения — то есть разница между «спокойным ламинарным» и «турбулентным
  глитч»-настроением из спека сейчас не рендерится вообще.
- God rays (для меланхоличных треков) реализованы в компоненте пост-процессинга
  и условно включаются по настроению, но требуют «источник» (`godRaysSource`),
  который никогда не передаётся — эффект физически не может ни разу
  сработать в текущем коде.
- Свайп вверх на мобильном ничего не делает — обработчик жеста не подключён;
  экрана «дискография/био артиста» из спека не существует вовсе.
- Только 3 из 26 треков ЗМП имеют полные профили (tempo/energy/mood/палитра) —
  остальные 23 текста лирики уже смигрированы и лежат в данных, но не включены
  в `track_ids` артиста и не появятся в библиотеке, пока для них не написан
  профиль.

## 5. Задача исследования

Дай приоритизированные, обоснованные рекомендации в трёх разделах. Для каждого
пункта — короткое обоснование (желательно со ссылкой на конкретный референс/
технику) и явная пометка **quick win** (можно сделать за один заход) или
**крупный скоуп** (требует отдельного этапа/архитектурного решения).

**Раздел A — Дизайн и арт-дирекшн.** Как поднять сцену от «работает и узнаваемо»
до «выглядит дорого и живо» — баланс bloom/экспозиции, чёткость и стиль
контуров, ощущение движения частиц (скорость/плотность/размер по разным
настроениям), палитра и контраст фона относительно текста лирики, как
использовать уже существующий, но не подключённый `noise_type` для реального
визуального контраста между агрессивными и меланхоличными треками. Отдельно —
как мог бы выглядеть незаспойленный god-rays-эффект, раз код для него уже есть.

**Раздел B — Функциональность «как у настоящего плеера».** Что ожидается от
современного веб-плеера музыки сверх того, что уже сделано (библиотека, поиск,
prev/next, авто-переход): очередь/плейлисты, громкость с визуальным слайдером,
seek-бар (в идеале с превью waveform), «избранное»/история прослушиваний,
шеринг ссылкой на трек и тайм-код, экран дискографии/био артиста (из спека, но
не реализован). Для каждого пункта — реалистично ли это на чистой статике без
бэкенда, или уже требует минимального бэкенда/хранилища.

**Раздел C — Внутренняя архитектура/производительность.** Как включить уже
написанный, но не подключённый код (аудио-кроссфейд через Web Audio Gain-узлы
при смене острова, BPM-пульсации), как реалистично откалибровать и проверить
лесенку деградации частиц на слабом железе (сейчас 100k/15k из спека — просто
цифры на бумаге, база в коде — 2000 без проверки на реальных устройствах), что
стоит добавить в модель данных трека/артиста уже сейчас (не меняя движок
рендеринга), чтобы будущий пайплайн загрузки пользовательских треков и
нейроадаптация легли без переделки — учитывая, что схема уже спроектирована
декларативно именно под это.

## 6. Формат ответа

Структурированный отчёт по разделам A/Б/В, с приоритизацией внутри каждого
(что делать в первую очередь) и явной пометкой quick win / крупный скоуп у
каждого пункта. Не предлагай то, что уже сделано (раздел 3) — фокус на
включении мёртвого кода (раздел 4) и на реальных пробелах.

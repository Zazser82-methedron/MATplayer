# MATplayer — дизайн-спек

Дата: 2026-07-24
Статус: одобрен пользователем в чате, ожидает финального ревью спека.

## 1. Идея и контекст

Генеративная 3D-платформа для «живого» знакомства со слушателем с исполнителями —
не список треков, а интерактивный аудиореактивный опыт: каждая строка песни
разворачивается как микро-сцена, персонаж-аватар исполнителя дышит/моргает/
реагирует, переходы между артистами — полёт камеры по единому 3D-пространству,
а не перезагрузка страницы.

Источник исследования: отчёт Google Gemini Deep Research (передан пользователем
2026-07-24), опирающийся на кейсы Active Theory, Album Atlas, ARKx (Coala Music),
PantoMatrix/JoyVASA. Референс-проект: `cupsize-v2-story` (`Projects\games\cupsize-v2-story\`) —
рабочий vanilla-JS canvas-движок с 26 сюжетными 2D-анимациями под альбом «ЗМП»
группы Cupsize и экспериментальная 3D-демка `compare8.html` (toon-shading, частицы,
bloom/fog/god rays). MATplayer — не расширение этого проекта, а полный редизайн
на новом стеке; `cupsize-v2-story` остаётся как архивный референс и не трогается.

Долгосрочный ориентир пользователя (важно для архитектурных решений, но НЕ входит
в объём этого спека): в будущем — реальный музыкальный сервис с загрузкой треков
пользователями, конкурирующий с SoundCloud/ВК Музыкой, плюс «нейроадаптация» через
локальные/облачные нейросети. Модель данных ниже спроектирована так, чтобы это
расширение не потребовало переделки движка рендеринга (см. раздел 8).

## 2. Объём этого спека

Полная платформа на N артистов сразу (не поэтапно один-артист-потом-остальные) —
явный выбор пользователя, несмотря на то, что это большой проект для одного захода.
Внутри реализации (следующий шаг — writing-plans) допустима разбивка на инкременты,
но сам дизайн описывает целевую архитектуру целиком.

**В объём входит:** статичный (без бэкенда) кураторский шоукейс, наполняемый вручную;
рендеринг, аудио-движок, синхронизация лирики, генеративная тема по треку, навигация
между артистами, UX-режимы, мобильная адаптация, производительность, доступность.

**Не входит:** аккаунты пользователей, загрузка треков конечными пользователями,
бэкенд/хранилище/стриминг-инфраструктура, авто-анализ произвольного загруженного
аудио, ИИ-генерация лицевой анимации/жестов (PantoMatrix/JoyVASA-класс решений).

## 3. Архитектура и стек

- **React + React Three Fiber + Drei** — декларативное описание WebGL-сцен,
  управление жизненным циклом ресурсов (lazy loading сцен/моделей по артисту).
- **Zustand** — состояние плеера (текущий артist/трек, время воспроизведения,
  UX-режим). Аудио-FFT-данные прокидываются в рендер-цикл через transient updates,
  минуя лишние ре-рендеры React-дерева.
- **Web Audio API** (`AnalyserNode` + `web-audio-beat-detector`) — анализ аудио
  в реальном времени.
- Кастомные GLSL-шейдеры (вершинные — curl noise для частиц; фрагментные —
  toon-shading/контуры/bloom/fog/god rays через post-processing pass).
- Сборка — Vite. Деплой — GitHub Pages (тот же паттерн, что и у остальных проектов
  пользователя: `git push` → сайт открывается по адресу `<user>.github.io/MATplayer/`).
- Репозиторий: `Projects\websites\MATplayer\` (новый git-репозиторий, ещё не
  инициализирован на момент написания спека).

## 4. Модель данных и контент-пайплайн

Каждый артист описывается JSON-профилем: имя, палитра по умолчанию, координаты
«острова» в 3D-атласе, список треков. Каждый трек — отдельный JSON-профиль в духе
отчёта Gemini:

```json
{
  "track_id": "cupsize_zppp",
  "tempo_bpm": 135,
  "energy": 0.85,
  "mood": "aggressive_grunge",
  "color_palette": { "background": "#0d0101", "primary": "#ff0055", "secondary": "#39ff14" },
  "shader_presets": { "noise_type": "simplex_curly", "outline_thickness": 0.05, "bloom_intensity": 1.5 },
  "lyrics_ref": "cupsize_zppp.lrc.json"
}
```

Лирика — построчный JSON (LRC-подобный формат), совместимый по данным с уже
существующими `lyrics.js`/`karaoke.js` из `cupsize-v2-story` (тайминги и текст
переносятся, формат конвертируется).

**Контент на старте:**
- **Cupsize / ЗМП** — реальный контент. 26 треков, реальные mp3, реальные тайминги
  лирики (перенос из `cupsize-v2-story`), профили `tempo_bpm`/`energy`/`mood`
  проставляются вручную по каждому треку.
- **1–2 placeholder-артиста** — синтетические профили с контрастным настроением
  (например один агрессивный, один меланхоличный — чтобы наглядно показать, что
  генеративная тема реально меняет визуал под артиста/трек), короткие demo-треки,
  без претензии на реальный релиз.

Схема данных спроектирована декларативно и без завязки на способ производства
профиля — сейчас профиль пишется вручную, но в будущем (отдельный проект с
бэкендом) те же поля может заполнять авто-анализ загруженного аудио, не меняя
ничего в движке рендеринга/темизации.

## 5. Рендеринг и визуальная система

**Базовый визуальный язык платформы — 3D toon-shading** (а не карандашный 2D-скетч
ЗМП, который остаётся эстетикой `cupsize-v2-story` как архивного проекта).

**Навигация — единый 3D-атлас.** Все артисты существуют в одном непрерывном
3D-пространстве как «острова»/узлы; переключение — полёт камеры по сплайнам
Безье, без перезагрузки страницы. Переход между сценами реализован без наложения
кадров: двухпроходный рендер во frame buffer, старая сцена рендерится в текстуру
и растворяется/вытесняется экранным шейдером (шторка/пикселизация/волна), пока
камера уже движется к новым координатам. Аудио параллельно делает кроссфейд
1.5–2 сек (тише старый трек, громче новый).

**Аватар исполнителя — стилизованный не-человеческий прокси**, не риг гуманоида:
геометрическая toon-форма/маска. Дыхание и «моргание» — процедурные, через
`THREE.Clock` и синусоидальные колебания (без morph targets, без индивидуальной
3D-модели под каждого артиста — прокси один и тот же, его контур/палитра/поведение
параметризуются JSON-профилем трека). Это решение выбрано специально, чтобы не
упираться в дорогой продакшн 3D-моделей под N артистов.

**Частицы** — `InstancedMesh` (не индивидуальные объекты — один draw call),
вершинный шейдер с curl-noise (по формулам из отчёта Gemini), амплитуда/скорость/
плотность зависят от FFT-данных (bass/mid/high) и от `energy` трека. При
`energy < 0.3` — плавное ламинарное движение частиц; при `energy > 0.8` —
турбулентные шейдеры с глитч-эффектами.

**Toon-shading пост-процессинг** (контуры, bloom, туман, god rays) — параметры
берутся из `shader_presets` трека и от `mood`: агрессивный грандж → резкие чёрные
контуры + постеризация текстур (cell shading); меланхоличное/романтичное → мягкий
рассеянный свет, god rays, густой туман, парящие частицы-пыльца, пастельная
палитра.

**Смысловые триггеры текста:** при появлении ключевых слов в строке лирики
(например «цветы», «плакать») параметры шейдера/форма частиц могут временно
меняться (круглые точки → текстурированные лепестки и т.п.) — опциональное
усиление, не блокирует MVP-версию.

## 6. Аудио и синхронизация лирики

`AnalyserNode` выполняет FFT над аудиопотоком; частотный диапазон делится на
bass/mid/treble по индексам бинов (формулы — см. отчёт Gemini, раздел 2). Усреднённые
нормализованные амплитуды передаются как uniform-переменные в шейдеры каждый кадр.
`web-audio-beat-detector` асинхронно считает BPM трека при загрузке — используется
для синхронизации пульсаций с сильными долями (независимо от частотного анализа).

Лирика синхронизируется построчно: в цикле рендера текущее время сопоставляется
с массивом таймингов из JSON; смена строки инициирует событие в Zustand-состоянии,
которое может менять параметры рендеринга (например переход куплет→припев меняет
толщину контура/интенсивность bloom).

## 7. UX-режимы, мобильная адаптация, производительность, доступность

**Три уровня активности:**
- **Focus Mode** — экран отдан сцене/шейдерам/крупному тексту, элементы управления
  скрыты, движение мыши — parallax камеры.
- **Ambient Mode** — после 10 сек бездействия UI управления растворяется
  (`opacity → 0`), остаётся только визуализация и караоке-текст.
- **Utility Mode** — любое движение мыши/клик мгновенно возвращает плоский UI
  (плейлист, громкость, эквалайзер) поверх 3D-сцены. Настройка «энергосбережение»
  жёстко фиксирует плоский UI без 3D.

**Мобильная адаптация:** портретная перестройка камеры (отдаляется по Z, смещается
вверх, освобождая нижнюю треть под караоке-текст) при `innerWidth < innerHeight`.
Тач-жесты: свайп влево/вправо — треки, свайп вверх — дискография/био, двойной тап —
пауза (без мелких кнопок поверх визуализации).

**Производительность:** `InstancedMesh` для частиц (один draw call вместо тысяч
объектов); динамическое снижение `pixelRatio` при просадке FPS (< 45 FPS → 1.0x);
лесенка деградации: отключение bloom/AA → отключение blur-пассов пост-процессинга →
снижение лимита частиц (100 000 → 15 000) → полная деградация 3D → 2D canvas/статичный
векторный аватар.

**Доступность:** медиа-запрос `prefers-reduced-motion` отключает динамические
полёты камеры, резкие вспышки, агрессивные аудиореактивные деформации — шейдеры
заменяются статичными градиентами, караоке-текст — простым изменением прозрачности
без эффектов прокрутки. Полная клавиатурная навигация (space — пауза/play, стрелки
влево/вправо — перемотка трека, вверх/вниз — громкость). Скрытый, но доступный
скринридерам DOM-текст лирики, дублирующий текущие караоке-строки в реальном времени.

## 8. Совместимость с будущим расширением (вне объёма, но учтено в дизайне)

Модель данных (раздел 4) намеренно декларативна и не завязана на способ production
профиля трека — сейчас профиль пишется вручную, в будущем те же поля может
заполнять авто-анализ загруженного пользователем аудио (бэкенд/аккаунты/хранилище —
отдельный будущий проект). Стилизованный не-человеческий прокси-аватар (раздел 5)
снимает необходимость индивидуального 3D-моделирования под каждого нового
исполнителя — это же свойство критично для сценария «пользователи сами загружают
треки», где заранее подготовленной 3D-модели исполнителя просто не будет.

## 9. Тестирование

- Юнит-тесты парсера лирики (JSON→массив таймингов) и расчёта частотных бинов
  (детерминированные функции, без WebGL-зависимостей).
- Визуальная/дымовая проверка через headless-браузер (по аналогии с существующей
  практикой `cupsize-v2-story`: `python -m http.server` + headless Edge/Chrome,
  ожидание маркерного `<title>`/флага готовности рендера).
- Ручная проверка деградации производительности (искусственно завышенный лимит
  частиц/принудительно низкий FPS) и `prefers-reduced-motion` в DevTools.

## 10. Открытые вопросы после этого спека

Ничего не блокирует переход к плану реализации; детали вроде точного набора
placeholder-артистов (2 или их состав) и конкретной точки для регенерации toon-
контуров можно уточнить на этапе реализации.
